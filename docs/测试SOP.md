# 测试 SOP

什么时候跑哪些测试（2026-11-04 用户定的；2026-11-21 加了"跑模型相关的几组"这一档，同一天改成几组同时跑）。测试是为了确认没改坏：按改动的范围跑，不多跑，也不少跑。

## 四种情况

### 不跑

- 只改文档、注释、待办：`docs/`、`claude/`、AGENTS.md、CLAUDE.md、`release/` 里的文字，代码里的说明和注释
- 改官网（`site/`）、宣传图：这些不在测试里，打开看效果
- 例外：加、删、改名了文件，或者改了文件开头说明的第一句，要重新生成代码地图（`python tools/code_map.py`），再跑 `python tests/test_code_map.py`（几秒）

### 只跑相关的一两组（几秒到一两分钟）

- 改了页面、底座（托盘、窗口、更新、设置、数据文件夹……）、测试工具、开发脚本：跑测这个功能的那一组
- 哪一组测它：在 [代码地图](代码地图.md) 的"测试（tests/）"一节搜改的文件名（每个测试文件那一行写着它测哪些文件）；也可以搜 `tests/` 里谁 import 了这个模块
- 单独跑一组：`python tests/test_sounds.py`（换成那一组的文件名）
- 没有测试管到的改动：写清楚是怎么验证的（打开页面看了、运行了一次脚本……）

### 跑模型相关的几组（`python tests/run_all.py --model`）

- 改了模型：识别（代码地图"模型"一节里的文件）、`config/` 里的规则、记录程序（`live_collect.py`、`in_match.py`、`post_match.py`、`calibration.py`）、录像（代码地图"录像"一节）。牵一发动全身，只有一局从头到尾的重放测试才看得出来
- 2026-11-21 用户定的（原话："只是改了录像功能，为什么还要测试直播正不正常？"）：以前这种情况跑全部，现在只跑两种组：① 用截图整局重放的组（它们把整个模型从头跑一遍）；② 测试文件里直接 import 了**这次改到的**程序的组（脚本看 git 里还没提交的改动，含新文件）。电竞、看直播、一键更新、云同步这些不用模型的组不跑。哪几组由脚本自动判断，开头一行写着跑几组、改到了哪些程序、整局重放跑不跑；新加的测试不用登记
- 同一天又定得更细（用户说测试太久，占开发时间）：
  - 改了 `config/` 里的某个规则文件（如 `hud.json`、`lang/en/summary.json`）：只算改了读它的那几个程序（代码里写着这个文件名的），不再当作整个模型全改了。参照图（`config/templates/`）认不出是谁读的，照旧当作全改了
  - 只改了录像（代码地图"录像"一节的四个文件，和它们读的 `recording.json`）：整局重放只跑最短的一组（简体中文的匹配局，约 17 秒），看记录程序带着录像的代码照样跑得通。重放时录像是关着的，测不到录像；录像关着时什么都不做，由"录像的录制核心"那一组查。约 1 分钟（以前 14 分钟）
  - 没有还没提交的改动（比如已经提交了）：当作模型全改了，整局重放都跑
- 结果表里每一组后面写着用了几秒

### 跑全部（`python tests/run_all.py`，约 4 分钟）

- 改了数据库 `storage.py`：几乎每一组都用到它
- 新赛季游戏更新以后
- 发新版本：`tools/release.py` 自己会先跑全部，没通过不打包，不用另外跑
- 放在后台跑，同时可以做别的；跑完看最后的"结果"表

拿不准算哪一种时，往多跑一档（比如不确定会不会影响记录程序，就跑 `--model`；不确定会不会影响别的功能，就跑全部）。

### 几组同时跑（2026-11-21 起）

- `run_all.py`（全部和 `--model`）每一组单独开一个进程，同时跑几组：默认是 CPU 线程数的一半（开发电脑 16 线程，同时跑 8 组）。全部从约 15 分钟降到约 3.5 分钟（11-21 实测 215 秒），一项检查都没少。以前一组接一组跑，大部分时间在等识别引擎，只用到一个核。同时跑时每组只用一个核（OpenCV 也设成单线程），不然各组互相抢，最慢的那组会拖到两倍多。现在卡在最慢的两组（游戏里的数据页、游戏画面比例，同时跑时各约 3.5 分钟）上，再快要把它们拆开或者记下识别结果
- 每组有自己的临时数据文件夹，互不干扰。上次用时久的先跑（记在 `build/test_times.json`，不进 git），总时间最短；每组跑完就把它的输出整段打出来，最后的结果表照原来的顺序
- `-j N` 改同时跑几组（`-j 1` 就是一组接一组，怀疑几组互相干扰时用）；一组 20 分钟没跑完当作卡住了，算没通过
- 打游戏时别跑：同时跑时 CPU 占得满

## 跑完以后

- 全部 ✅ 才算没改坏。"⏭ 跳过"是找不到截图（截图只在开发者电脑的 `captures/` 里），不算通过，要说出来
- 有 ❌：先修好再提交。不改测试里的正确答案去迁就代码，除非确认原来的答案错了，并告诉用户
- 提交说明的"怎么验证的"里写跑了哪几组、结果怎样

## 测试是怎么做的

- `tests/fake_game.py` 用"假摄像头"把真实截图按顺序喂给记录程序，数据写进临时文件夹（不碰正式数据），时钟是假的。正确答案写在 `tests/` 里的 CSV 和测试文件里
- 每一组是一个 `tests/test_*.py`，有一个 `main()`：返回 True（通过）、False（没通过）、None（跳过）。新加的组要加进 `run_all.py` 的 `TESTS`（写模块名，如 `"test_sounds"`）。`run_all.py` 用 `--one 模块名` 在单独的进程里跑一组
- 测试只 import 项目代码，项目代码不能 import 测试（否则 PyInstaller 会把测试打进安装包）。要用 `tools/` 里的脚本时，用 subprocess 运行它
