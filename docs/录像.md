# 录像（整局录像 + 进度条上的事件）

2026-11-20 起开发。做法是用户 11-19、11-20 定的；第 0 步实测（开销、断了能不能接上、录像里的小字读不读得准、声音对不对得上）见 [录屏实测.md](录屏实测.md)，实测用的脚本是 `tools/rec_probe.py`、`tools/rec_audio.py`。

## 定下来的

**核心诉求（2026-11-21 用户定的）**：做一个专注于 Apex 的录像功能，和 Outplayed（Overwolf）、NVIDIA 的录像、OBS 等主流录屏方案比，各方面都要有决定性的优势。Claude 的看法：画质 / 文件大小、对帧数的影响这几项大家用的是同一块显卡编码器，做到不输、略好；决定性的优势要靠"专注 Apex"（认得出的事件和准确度、和战绩连在一起、自动剪高光、省硬盘的保存策略、国内能用、只用被动接口）；资源占用现在明显落后（11-21 那局对局中 Evo 约 2.5 个核、200 多 MB，识别和录像一起算），要先解决。和各家的对比、分步路线见下面"和别家比"

**Outplayed 录像实测（11-21，用户 11-13 用 Outplayed 录的一局，1080p 60 帧 12000 kbps，`E:\Outplayed\`）**：14 分 34 秒 1.27 GB。画面 H.264 High、**整局固定 12.0 Mbps（不按画面增减）**、开着 B 帧；声音三轨（游戏、麦克风、混在一起的，合计约 0.4 Mbps）。Evo 11-21 那局（1080p 60 帧标准）：画面 5.5 Mbps、没开 B 帧、一轨声音。**用户 11-21 定的目标：文件大小和 Outplayed 差不多就行**。Evo 选 1080p 60 帧"很高"时约 12.4 Mbps，同样 14 分 34 秒约 1.28 GB，已经和它一样；默认"标准"约 0.57 GB，不到它一半。它开着 B 帧；Evo 以前不开（照第 0 步实测脚本写的，没有特别的原因），11-21 用户定了开（AV1 先不做），见下面"怎么做"的编码

已知问题：Outplayed 的事件接口队友补掉的人不发击杀事件；整局模式在被淘汰后把录像切成两段；Overwolf 11-01 起只批准用它自家变现的应用。来源链接在 11-21 那次对话的调研报告里（Overwolf GEP 文档、game-events-status.overwolf.com、NVIDIA 的游戏数据文件、medal.tv/auto-clipping、LTT Labs 经 GIGAZINE 转述等）。

**没人做好、Evo 能拉开差距的地方**：
1. 录像和战绩连起来：名次、准确的伤害、RP 变化、段位，别家都没有（Outplayed 也只有名次和偏高的伤害）
2. 免费、无广告、不注入、开源、又认得 Apex 事件：现在没有这样的（能认的只有 Outplayed、Moments，各有代价）
3. 整局录像 + 进度条事件 + 过期只留高光
4. 事件准确度：用画面上的计数（总结页、右上角）对账，知道漏没漏（Outplayed 队友补刀不算、击倒和击杀分不清的问题，Evo 能补）
5. 国内：B站、抖音、微信、小程序；别家的分享和账号都在海外
6. 轻量：能认事件的都是常驻的大平台，轻量的（Game Bar、显卡驱动自带）又不认事件

**Claude 建议的路线**（等用户定先后）：
- 现在（0.7.0b）：整局录像 + 事件（已做：击倒、助攻击倒、击杀、助攻、倒地、成盒、被复活、冠军）+ 画质四档。用打包好的版本量对局中的占用
- ① 录像和战绩深度连接：录像页按传奇、地图、模式、事件找；每局的 RP 变化；"今天所有击杀"
- ② 自动高光片段：按事件切（前几秒、后几秒，不重新编码），一键合集。**11-21 做好了（合集还没做）：见上面定下来的第 10 条**（录制模式可选"只录高光"、整局录像上一键保存高光、每种事件各自的前后秒数）
- ③ 只留高光的保存策略：整局留 N 天，过期只留高光，省硬盘
- ④ 每局对账：进度条上的击杀、助攻、击倒和总结页比，对不上就提示可能漏了（和"从画面记下一局里几乎所有事件"那条一起做）
- ⑤ 国内分享：用已有的 B站扫码登录一键传 B站；小程序在手机上看高光
- ⑥ 更多事件：队友倒地 / 成盒、被谁击倒、伤害曲线、救人；AV1（要换分段格式）
- 资源：对帧数的影响按"不比 NVIDIA 自带录像大"来衡量（游戏开着帧数显示时可以读右上角的 FPS 来量，EA 反作弊在时 PresentMon 用不了）

## 怎么做（第一版）

- **独立的 ffmpeg 进程**：记录程序开、关它。放进 Windows 的作业对象，Evo 崩了、被结束，它也跟着退，不会一直往硬盘写
- **什么时候录**：一局开始时开始（看到开局画面或自己的界面），一局结束时停（淘汰画面、冠军、返回大厅）。不在对局里不录
- **抓屏**：`gfxcapture=hwnd=<Apex 的窗口句柄>…`，按设置的分辨率在抓的时候缩放。抓不到再换 `ddagrab`
- **找 Apex 的窗口不打开游戏进程**（原则 1）：进程号从进程列表里拿（`game_detect`，本来就不打开进程），窗口用 `recorder.find_window` 按"窗口归哪个进程"找，把窗口句柄交给 ffmpeg。不用 ffmpeg 的 `window_exe`：2026-11-20 看 ffmpeg 源码发现，它要对每个窗口所属的进程（包括 Apex）打开一个查询句柄读程序名（`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`，不读内存，任务管理器也这样，但还是算碰了游戏进程）。11-19、11-20 用 `rec_probe.py` 测"只抓 Apex 窗口"时用过它几次，之后改掉了。Windows Graphics Capture 本身只向 Windows 要这个窗口合成好的画面（和截图工具、Xbox Game Bar 一样），不碰游戏
- **编码**：显卡硬件编码，NVIDIA > AMD > Intel。没有硬件编码器的电脑不开放这个功能（不用 CPU 软编）。**开 B 帧**（11-21 用户定的）：N 卡 3 个（B 帧也当参照）、AMD 2 个、Intel 没测过先不开（`config/recording.json` 的 `b_frames`）；显卡不支持时检测编码器那一步自动不开。同样码率下 N 卡慢画面略清楚、打架不变，AMD 都好约 2 分（VMAF），文件不变大；拼接、空档、事件位置、声音对齐都验过，实测见 `docs/录屏实测.md`"B 帧"
- **写文件**：每开一次 ffmpeg 写一个 MPEG-TS（程序崩了也不会坏；`-mpegts_copyts 1` 让文件里的时间戳就是原来的时刻），断了重开就再写一个。一局结束首尾相连地读（`concat:` 协议）拼成一个 MP4，不重新编码。拼的时候加 `-copyts -start_at_zero -dts_delta_threshold 1000000`：断掉的空档原样保留，不然 ffmpeg 会把 10 秒以上的空档挤掉，后面的事件就对不上了。整局录像不用切成 2 秒一段（剪高光时再切）
- **崩了以后**：上次没拼完的分段文件，下次拼成名字带"_未完成"的 MP4（只有画面）
- **时间**：每一帧的时间戳 = 抓到它时电脑的时钟减去开始时刻（微秒），所以事件的时刻能直接对上录像里的位置
- **断了就重开**：切窗口、切显示模式、弹管理员确认框时桌面复制会失效，ffmpeg 直接退出、不会自己恢复。马上重开（第一次可能被拒，再开一次），实测断 1–2.5 秒。Windows Graphics Capture 遇到这些时怎么样，要在对局里实测
- **声音**：按进程录音（`tools/rec_audio.py` 的做法），每一包带 Windows 给的时刻，拼 MP4 时按这个时刻对齐画面
- **事件**：
  - 倒地 `knocked`、被扶起 `revived`、成盒 `dead`、被复活 `respawned`、冠军 `champion`：看 InMatchWatcher 记下的状态，不另外认画面
  - 击倒对手 `knock`（11-20，用户的提示）：画面中间那一行"击倒 名字 +150"，在一条横带里找"击倒"两个字（只比外观，录像开着时每截一张看一次，约 1 毫秒；`hud.knock`，规则 `config/hud.json` 的 knock，实测见 `docs/识别经验.md`"中间那一行'击倒'"）。没看到 0.6 秒以上才算下一次；还在显示但左右挪了 20 以上（换了名字）也算。用 11-20 那局的录像整段验过：只认出一次，时刻对。

## 实测踩过的坑（照着做）

- **录"除了 Apex 以外的声音"不能用 Windows 的排除模式**（`PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`，2026-11-21 实测）：在这台电脑上排除谁都没用，照样全录进去。原因是装了 HyperX NGENUITY（耳机的音效软件，`hxn-srv-audio-engine.exe`），所有程序的声音先交给它、加工后由它再放一遍；别人也报告过这个参数被忽略（miniaudio #484），OBS 的录音插件也改成自己列出程序逐个录。"只录某个程序"（包含模式）照样准，有音效软件也不受影响。所以"电脑上所有的声音"直接用系统内录（默认播放设备，录到的是音效软件加工前、所有程序混在一起的声音），不做"除了游戏"
- 系统内录、麦克风和按进程录音用同一个接口（`ActivateAudioInterfaceAsync`，给默认播放 / 录音设备的接口名，跟着 Windows 换默认设备），每一包都带 QPC 时刻：同一个响声，系统内录比按进程录早 5–11 毫秒（不到一包 10 毫秒），听不出来。`process_audio.py` 单独试：`python code/process_audio.py system 5 x.wav`、`... mic 5 x.wav`
- 能列出"正在放声音的程序"（Windows 的音频会话 `IAudioSessionManager2`，只读列表）：这台电脑上有微信、Discord、Steam、小黑盒、Chrome、NGENUITY。用户定了不按语音软件分，没用上，以后要"只录某几个程序"时可以用
- 时间戳要用微秒（`-enc_time_base:v filter`），不能取整到 1/60 秒：取整后有的帧撞在同一个时刻被丢掉
- 把分段接起来要首尾相连地读（`concat:` 协议），不能用 ffmpeg 的拼接列表：时间会越接越偏
- 从录像里按时间取一帧用 `select` 滤镜 + `-fps_mode passthrough`，不用 `-ss`
- 存图、读图不要用 `cv2.imwrite` / `cv2.imread`：路径里有中文时会悄悄失败
- 剪高光直接切（`-c copy`）时 `-ss` 要**正好写关键帧的时刻**（精确到微秒）：试过晚 0.0005 秒，那个关键帧在片段里落在 0 之前，播放器不显示它，片段从下一帧（B 帧）开始；正好写时第一帧是关键帧、在 0 秒，开头和原片逐帧一样（N 卡 3 个 B 帧的测试录像、11-21 那局真录像各 4 段都核对过）。结尾因为 B 帧少最后两三帧（约 0.05 秒），看不出来。ffmpeg showinfo 的 `pts_time` 只有 6 位有效数字（1000 秒以后只到 0.01 秒），要用整数的 `pts` × 时间单位算
- 11-21 跑测试时，测试录像（N 卡开 B 帧）的关键帧三次里两次成对出现（如 1.9996 秒、2.0303 秒挨着两个，强制关键帧后面几帧又一个）；不影响剪高光。**同一天 Claude 查了：和 B 帧无关，是编码器两套放关键帧的规则碰上了**：`-g`（每 120 帧一个）和 `-force_key_frames`（每 2 秒一个）。画面每秒稍多于 60 帧时，第 120 帧比 2 秒早一点到，两套各放一个，差一两帧。实测（只抓一个一直在动的测试窗口，每次录 10 秒）：开 3 个 B 帧和不开各录两次，4 次里 3 次在 2 秒附近成对（如 1.9975、2.0141 秒），开不开 B 帧都有；高光窗口跑 8 组测试同时跑时，测试画面录 8 秒在 2 秒、8 秒附近各一对（录像中途也会有）；Claude 单独录测试画面（每秒 60 或 58 帧、第一帧晚 0.45 秒、CPU 占满）、桌面复制都没复现；11-21 00:33 那局真录像（不开 B 帧，10 分钟）309 个关键帧正好每 2 秒一个、一对都没有。影响：每出现一次多一张完整的图（几十 KB），同样码率下别的画面分到的少一点。**`-g` 放宽到 240 帧（只留按时间的那套）同样只抓窗口录 4 次：一对都没有**。**用户 11-21 定了改，进 0.7.0**：`recorder.encoder_args` 的 `-g` 改成每 2 秒帧数的两倍（60 帧时 240），只在按时间的那套失灵时兜底。改完用精简版 ffmpeg 真抓屏录了 8 次（只抓窗口、桌面复制，开不开 B 帧）、`tests/test_recorder.py` 单独 3 次、`run_all.py --model`（几组同时跑）2 次，关键帧都是每 2 秒一个，一对都没有
- 在录像上读界面要按游戏自己的画面比例找位置（`game_aspect.py`）：拉伸分辨率时只按截图的比例找会读不出
- **录像结尾常常已经拍到了总结页 / 经验值页**（2026-11-25 重放 12 段时发现）：一局结束后还要录 3 秒，玩家手快时这 3 秒里已经点进了这两页，12 段里 9 段是这样。所以"录像里的一局"不等于"没看总结页的一局"；录像重放工具（`tools/replay_recordings.py`）默认用 Evo 自己认画面的代码认出这两页、从那一帧起换成黑图，再查临时数据库的来源确认没读到，结论见 `docs/识别经验.md`"跳过总结页时备用来源准不准"
- EA 反作弊在运行时，管理员也开不了 Windows 的事件记录（ETW），PresentMon 量不了帧数；桌面复制、Windows Graphics Capture、按进程录音都不受影响
