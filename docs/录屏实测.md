# 录屏实测（高光录屏第 0 步）

2026-11-19 起。要不要做"高光自动录屏"、怎么做，先用实测的数来定。方案是：一个独立的 ffmpeg 进程，用桌面复制抓屏（和 dxcam 同一个接口，不碰游戏），显卡硬件编码，2 秒一段存在硬盘上，由 Evo 认出的事件决定留哪几段。还没定的事见 todo.md"高光录屏"那条。这一步只在测试时用 ffmpeg，Evo 本身不改。

- 工具：`tools/rec_probe.py`（录屏、量开销、比对），`tools/rec_audio.py`（只录一个程序的声音）
- 录下的东西放在 `captures/rec_probe/<时间>/`：不进 git，很大，测完就删
- 下面的 `python` 都是指 `E:\Evo\.venv\Scripts\python.exe`，在 `E:\Evo` 里运行

## 已经在本机试过的（不开游戏）

2026-11-19，RTX 5060 Ti（屏幕接在它上面）+ AMD 核显，2560×1440 240Hz，ffmpeg 9.0.2，桌面基本不动。

| 项目 | 结果 |
| --- | --- |
| 抓屏 | 桌面复制（ffmpeg 的 `ddagrab`）、Windows Graphics Capture（`gfxcapture`）都抓得到整个屏幕 |
| 编码器 | `h264_nvenc`、`hevc_nvenc`、`av1_nvenc` 都能直接拿显卡里的画面编码。AMD 核显的 AMF 只能先拷进内存再编码（正常：屏幕接在 N 卡上） |
| 缩到 1080p | 在显卡上缩放（`scale_d3d11`）建不起来（"Could not create the texture"），CUDA 也接不上，所以第一版录原分辨率 |
| 只录屏 | ffmpeg 占 CPU 约 4% 个核，内存 81 MB，每秒 59.9 帧（设定 60） |
| 录屏，同时每 0.3 秒给 Evo 送一张原图（"不用 dxcam、从 ffmpeg 拿图"的想法） | ffmpeg 占 CPU 6.9% 个核，内存 125 MB；Python 这边收图 7.4% 个核。**录像只剩每秒约 56 帧，少了约 6%**：从显卡拷图和抓屏在 ffmpeg 的同一个线程里，拷图时抓屏要等。原图里加转成 BGR 那一步时 ffmpeg 占 15.5%，已改成不转换 |
| 模拟读结算页（引擎读一整张图，5–8 秒） | 收图的线程一直在读：两张原图之间最长隔 0.36 秒，录像没受影响 |
| 两个抓屏放进同一个 ffmpeg | 不行：同一个程序对同一块屏幕只能开一次桌面复制。所以要从 ffmpeg 拿图，只能把同一路画面分成两路 |
| 只录一个程序的声音 | 能用（Windows 的按进程录音）。每一包声音带着 Windows 给的时刻 |
| 声音和画面对齐 | 画面和声音各自的时刻都准：方块变白后 5–21 毫秒录进画面（一帧之内）；嘀声 28–59 毫秒后录进声音（这是 Windows 播放声音本身的延迟）。剪出来的片段里声音比画面晚 27–39 毫秒，看不出来 |
| Evo 崩了，ffmpeg 会不会一直录 | 不会：ffmpeg 放进了 Windows 的"作业对象"，Evo 被强行结束时它也跟着退 |
| 对照：dxcam 每 0.3 秒截一张 | 源码版（`python.exe`）占 415% 个核，就是 todo"源码版截屏时 CPU 很高"那条，不能当对照。dxcam 的开销看安装版日志里的"占用"（11-10 是 15%） |
| 录像里的小字 | 拿 `captures/samples/对局中.png` 编码成录像再读右上角：剩余小队 18、RP −65，和原图一样。这是静止的画面，比实战乐观，要用实战录像再比 |

脚本里已经处理好的两个坑：
- 时间戳要用微秒，不能取整到 1/60 秒：取整后有的帧撞在同一个时刻被丢掉，录像只剩 58.7 帧
- 把分段接起来时要首尾相连地读（`concat:` 协议），不能用 ffmpeg 的拼接列表：拼接列表按每段的"时长"排下一段，帧间隔不均匀时每段差两三毫秒，10 秒就偏了十几毫秒

## 准备

1. **ffmpeg**：本机已经用 winget 装了 `Gyan.FFmpeg` 9.0.2，脚本自己找得到。别的电脑上用 `winget install --id Gyan.FFmpeg -e` 装，或者设环境变量 `EVO_FFMPEG` 指向 ffmpeg.exe。这个完整版的 ffmpeg.exe 有 217 MB，只在测试时用
2. **PresentMon**（量帧数，Intel 开源；只读 Windows 的事件记录，不碰游戏）：在 GitHub `GameTechDev/PresentMon` 的 Releases 里下载 `PresentMon-2.6.0-x64.exe`（约 1 MB）。要在**管理员身份**的 PowerShell 里运行
   - **EA 反作弊在运行时用不了**（2026-11-19 实测）：`EAAntiCheatService`（Apex 的 Javelin）在运行时，管理员也开不了这类记录：PresentMon 和 Windows 自带的 `logman` 都报"拒绝访问"，换成和显卡无关的记录也一样。停掉这个服务（`Stop-Service EAAntiCheatService`）以后马上就能开。Windows 的默认权限没被改过（管理员有完全控制）。开 Apex 时这个服务一定在运行，所以第 2 步要先找一种在它下面能用的量法，见第 2 步开头
3. **开安装版 Evo**（`E:\Evo Tracker`）照常记录：第一版就是"Evo 用 dxcam 截图，另开一个 ffmpeg 录屏"。不要同时开源码版
4. **硬盘**：游戏里画面一直在动，按 22 Mbps 算，每 10 分钟约 1.6 GB

## 步骤

### 1. 看能用什么（开着 Apex，约 2 分钟）

```
python tools/rec_probe.py check
```

记下哪些编码器打了 ✓，以及"gfxcapture 只抓 Apex 的窗口"能不能用。最后一行会给出下一步的命令。

### 2. 帧数（靶场，约 15 分钟）

**还没定怎么量**：EA 反作弊在运行时 PresentMon 开不了（见"准备"第 2 条）。用户 11-19 定的：量不了就先跳过这一步，直接测录屏本身（第 1、3–5 步）；帧数先用 NVIDIA App 的统计数据（Alt+R）大概看一眼开、关录屏差多少。可以试的办法，都还没试过：
- NVIDIA 自己的：在游戏里按 Alt+R 打开 NVIDIA App 的统计数据，看得到帧数，就说明 NVIDIA 的服务在 EA 反作弊下能读帧；再用 NVIDIA FrameView 把帧数存成 CSV（它存的格式应该和 PresentMon 一样，拿到文件先核对列名，`fps` 子命令认 `MsBetweenPresents` 这一列）
- 先开 PresentMon、再开游戏：看 EA 反作弊启动以后已经开着的记录还在不在（可能被关掉，也可能游戏不让启动）

下面是能用 PresentMon 时的做法：

1. 进靶场，站在一个固定位置看同一个方向，不动鼠标。画质设置和平时一样
2. **关录屏**，在管理员 PowerShell 里量 60 秒。`--delay 15` 是留 15 秒切回游戏：

   ```
   .\PresentMon-2.6.0-x64.exe --process_name r5apex.exe --process_name r5apex_dx12.exe --output_file off1.csv --delay 15 --timed 60 --terminate_after_timed
   ```

3. **开录屏**：在另一个窗口运行 `python tools/rec_probe.py record --minutes 3 --label 靶场`，等它说"开始录"以后，用同样的 PresentMon 命令量，文件名换成 `on1.csv`
4. 关、开再各量一次（`off2.csv`、`on2.csv`），交替着量，免得显卡越跑越热影响结果
5. 比较：

   ```
   python tools/rec_probe.py fps --off off1.csv off2.csv --on on1.csv on2.csv
   ```

6. 想单独看"给 Evo 送图"的影响：开录屏那一步改用 `record --no-frames`，再量一组

**过关**：平均帧数和 1% 低帧都只掉 3% 以内（方案建议的门槛，你来定）。

### 3. 打两局真实对局（每局约 25 分钟）

```
python tools/rec_probe.py record --minutes 25 --label 对局1
```

- 开局前开始录，打完自动停。也可以按 Ctrl+C 提前停
- 默认同时录 Apex 的声音、每 0.3 秒给 Evo 送一张原图、每 15 秒存一张原图。"读结算页时送图会不会堵住"已经在本机试过（加 `--ocr-every 60` 可以再试），对局中别开：引擎一读就占好几个核，游戏会卡一下
- 打的时候故意做几件事，看录屏断不断、断了能不能自己接上：
  - Alt+Tab 切出去再切回来，做一次
  - 在大厅里把显示模式在"全屏"和"无边框窗口"之间切换一次
  - 弹一次管理员确认框（比如右键以管理员身份打开记事本），做一次
- 停下后会打印结果，也存在那次录像文件夹的 `summary.txt` 里：ffmpeg 的 CPU 和内存、文件多大、录像里每秒实际几帧、送图有没有断、断了又重开了几次
- 第二局用 `--no-frames` 打，对比不送图时的开销

**过关**（方案建议的门槛，你来定）：
- ffmpeg 只录屏时占不到 5% 个核
- 录像每秒帧数在设定的 95% 以上
- 切窗口、切显示模式以后几秒内自己接上

### 4. 录像里的小字读不读得准（打完第 3 步以后）

```
python tools/rec_probe.py ocr captures\rec_probe\<第3步的文件夹>
```

它把对局中每 15 秒存的那张原图，和录像里同一时刻的那一帧，都拿 Evo 读右上角的方法读一遍，逐项比较剩余小队、击杀、助攻、伤害、RP。

**过关**：全部一样。不一样的地方，就是以后"赛后看录像再识别"会读错的地方。

### 5. 声音

1. **漂不漂**（不用开游戏，10 分钟）：

   ```
   python tools/rec_probe.py avsync --seconds 600
   ```

   - 屏幕左上角会出现一个黑方块，每 2 秒闪白一下、嘀一声
   - 期间别把别的窗口拖到它上面，也别关声音
   - 结果会告诉你声音比画面晚多少、每 10 分钟漂多少
   - **过关**：漂移在 20 毫秒以内
2. **游戏里听**：第 3 步录的时候打完一波交火，按 Ctrl+C 停，再剪最后 30 秒、打开播放：

   ```
   python tools/rec_probe.py clip captures\rec_probe\<文件夹> --last 30 --open
   ```

   看枪声和开火的画面对不对得上，声音有没有断断续续。也可以用 `--at 秒数` 剪中间的某一段（秒数从开始录算起）。

### 6. 可选

- **只抓 Apex 的窗口**（如果第 1 步说能用）：`record --source gfxcapture --minutes 5`，看会不会有黄边、QQ / 微信弹窗还录不录得进去、占用和桌面复制比怎么样
- **双显卡笔记本**：在笔记本上跑 `check`，看用核显编码（Intel 是 `h264_qsv`）能不能直接拿显卡里的画面

第 1 步（11-19，开着 Apex）：桌面复制、只抓 Apex 窗口（gfxcapture）都抓得到；NVENC 三种都能直接拿显卡里的画面编码；按进程录音、作业对象都正常。不用管理员权限。

两局都是 2560×1440 60 帧、h264_nvenc 22 Mbps、送原图、录 Apex 的声音。游戏是 2560×1600（16:10）拉伸到 2560×1440 的屏幕。

- **第二局**（11-19 22:23，匹配，8 杀 2930 伤害；录了 21.2 分钟）：开始录以后、排队之前，在大厅里切了窗口、切了显示模式、弹了管理员确认框

踩到的坑（脚本都已修）：
- 录像文件夹名里有中文时，原图一张都没存下：`cv2.imwrite` 存不了中文路径，也不报错。改成先编码再写文件
- 读右上角要按游戏自己的画面比例找位置：拉伸分辨率时只按截图的 16:9 找，原图也读不出。`record` 现在把游戏的画面比例记进 `meta.json`，`ocr` 按它找
- 送图挑帧：ffmpeg 的 fps 滤镜默认（`round=near`）挑的是"这一刻前后 0.15 秒里最后一帧"，原图的内容比标的时刻晚 131–150 毫秒（第二局逐张量的；用 testsrc2 核对过：near 晚 150–183 毫秒，`round=up` 晚 0–33 毫秒）。已改成 `round=up`。**以后 Evo 从 ffmpeg 拿图，要知道每一张的准确时刻**，不能按"第几张 × 0.3 秒"算
- 从录像里按时间取一帧：用 `-ss` 不准，改用 `select` 滤镜 + `-fps_mode passthrough`。对照时也要加 `-fps_mode passthrough`，不然 ffmpeg 会补帧、丢帧，帧的序号和时间对不上（一开始因为这个以为取帧晚了 60–90 毫秒）
- 比原图和录像：在原图的时刻附近几帧里，用全分辨率挑平均差最小的那一帧（同一帧只差压缩，约 2–5；相邻的帧差得多）。一开始比的不是同一帧，交火时伤害对不上（620 对 602），以为是录像糊了
- 重开 ffmpeg 以后，汇总里送图的张数只算了最后一次的。已改成累加

用户 11-19 定的：剩下的（游戏里只录屏、不送图的开销，10 分钟的声音漂移）不补测，直接进入下一步。

测完把 `captures/rec_probe/` 删掉。

## B 帧（2026-11-21）

起因：用户 11-13 用 Outplayed 录的那局开着 B 帧，Evo 一直是 `-bf 0`（照第 0 步实测脚本写的，没有特别的原因）。用户要开 B 帧（AV1 先不做）。

**画质**：11-20 那局（2560×1440 22 Mbps，原片清楚）截三段各 20 秒（搜东西 60 秒起、打架 140 秒起和 215 秒起），缩成 1080p、按 60 帧重新排好时间、存成无损的参照；再用和 `recorder.encoder_args` 一样的参数压成标准档 5.6 Mbps，只改 B 帧，和参照逐帧比 VMAF（满分 100，差 6 分左右一般人才看得出）。完整版 ffmpeg 9.0.2，RTX 5060 Ti、AMD 核显。

| | 搜东西 | 打架 1 | 打架 2 |
| --- | --- | --- | --- |
| N 卡 不开（以前） | 92.8（5.85 Mbps） | 84.7 | 84.3 |
| N 卡 2 个 | 93.8 | 84.3 | 84.1 |
| **N 卡 3 个 + B 帧也当参照（`-b_ref_mode middle`，现在用的）** | **94.1（5.55 Mbps）** | **84.4** | **84.3** |
| N 卡 3 个 + 往后看 20 帧（`-rc-lookahead 20`） | 94.0 | 84.4 | 84.4 |
| N 卡 不开 + 往后看 20 帧 | 92.8 | 84.7 | 84.3 |
| AMD 核显 不开 | 90.2 | 78.1（5.9 Mbps） | |
| **AMD 核显 2 个（现在用的）** | **92.1** | **80.1（6.2 Mbps）** | |

结论：N 卡在打架时没差别、慢画面略好；AMD 两种都好约 2 分（AMD 本来比 N 卡差一截）；"往后看"没用。文件大小基本不变（码率是固定的；桌面这种几乎不动的画面开了反而小三分之一）。Intel 没有显卡，没测，先不开。

**录像流程**（改好的 `recorder.py`，`tests/test_recorder.py` 里真的录的那几项：拼接、断了 11 秒的空档、事件位置、声音对齐到 0.03 秒以内、崩了恢复、三条音轨）：完整版和精简版 ffmpeg（`dist/ffmpeg`）、N 卡和 AMD 核显都全过，MP4 里真有 B 帧（N 卡 3 秒里 I 2、P 45、B 133）。真的从显卡抓画面（开一个一直在动的测试窗口，各录 10 秒，精简版 ffmpeg、N 卡）：

| | 开 3 个 B 帧 | 不开 |
| --- | --- | --- |
| 只抓窗口（gfxcapture，1280×720） | 580 帧，59.9 帧/秒，没断 | 581 帧，59.9 帧/秒 |
| 桌面复制（ddagrab，2560×1440） | 584 帧，60.0 帧/秒，没断，12.1 MB | 585 帧，60.1 帧/秒，18.5 MB |

没在游戏里录过；Intel、独立 AMD 显卡、老 N 卡（不支持 `b_ref_mode` 的）没试过：检测编码器那一步开了 B 帧编不了会自动不开（`recorder.pick_encoder`），所以最坏是和以前一样。

注意（比画质时踩的坑）：ffmpeg 的 psnr / ssim / libvmaf 按时间戳配对两路画面。录像是可变帧率，压出来的那份时间被取整，两边的时间单位也不一样（MKV 按毫秒），会配错帧（60 Mbps 也只有 27 dB）。要先把参照按 60 帧排好（`setpts=N/60/TB`），比的时候两边都 `settb=1/60,setpts=N`，按第几帧配对。

## AV1 的分段格式（2026-11-26）

起因：ffmpeg 9.0.2 读写 TS 的代码里没有 AV1（11-20 看源码），按 H.264 那样分段写 .ts 录不成 AV1。用户 11-26 在 QQ 群统计，大部分玩家的显卡够新，要加回 AV1。这台电脑：RTX 5060 Ti（`av1_nvenc` 能用，开 3 个 B 帧、`b_ref_mode middle` 也行）+ AMD 核显（`av1_amf` 不能用：这代核显编不了 AV1），Intel 的没有。测试画面 testsrc2 + `realtime`，时间戳照录像的做法（`setpts=RTCTIME-t0`、`-enc_time_base:v filter`），录两段：第一段 6 秒正常停，隔 12 秒再录 6 秒、硬杀（像 Evo 崩了）。

| 分段格式 | 硬杀的那段 | 第二段的时间 | 拼成 MP4 |
|---|---|---|---|
| MKV（matroska） | 读得回来，丢了最后约 2.4 秒（这时还没加下面两个参数） | 照存原来的时刻（18.384 秒），只到毫秒 | 拼接列表 + 每段写 `duration`（= 下一段第一帧 − 这一段第一帧）：第二段正好从 18.334 秒开始（18.384 − 0.05），空档一点不差 |
| 分段的 MP4（`frag_keyframe+empty_moov`） | 读得回来 | **每段都从 0 重新算**，开局的时刻丢了 | 不能用 |
| H.264 写进 MKV（对照） | 读得回来 | 照存，只到毫秒 | 能拼，但开头几帧、偶尔中间两帧落在同一毫秒，拼的时候报"Non-monotonic DTS"、往后挪 1 个单位；B 帧的解码时间要从显示时间倒推 |

所以 AV1 写 MKV、H.264 照旧写 .ts（用户定的：0.7 验证过的不动）。拼接列表不写 `duration` 时按每段自己的长度接，会把空档挤掉（docs/录像.md 写过"时间会越接越偏"）。

**硬杀时 MKV 丢多少**（精简版 ffmpeg，640×360 AV1，录几秒就硬杀，能解出几帧）：

| 参数 | 录 1.5 秒杀 | 录 2.5 秒 | 录 4 秒 |
|---|---|---|---|
| 只加 `-cluster_time_limit 1000` | 文件是空的（0 字节） | 117 帧 | 117 帧（文件正好 256 KB） |
| `-cluster_time_limit 1000 -flush_packets 1` | 60 帧 | 120 帧 | 181 帧 |
| `-cluster_time_limit 500 -flush_packets 1` | 61 帧 | 120 帧 | 213 帧 |

不加 `-flush_packets 1` 时 ffmpeg 先攒满 256 KB 才写盘，刚开录就被杀什么都没有；加了以后每写完一块马上落盘，最多丢约 1 秒（开头还有约 0.4 秒是编码器启动）。录像用 1000 + flush（`recorder.SEGMENTS`）。TS 本来就随写随落盘，不用加。

**Evo 窗口放得了吗**：WebView2（Edge 158）里放 AV1 的 MP4：`canPlayType` 是 probably，`decodingInfo` 说用显卡解码（powerEfficient），画面正常。这台电脑装着微软的"AV1 视频扩展"（2.0.35），没装的电脑放不放得了没核实（Edge 以前靠这个扩展放 AV1），所以设置页按这台电脑 WebView2 自己说的算，放不了就不让选。

精简版 ffmpeg 加了 AV1 的三个编码器、dav1d 解码器（截缩略图、读第一帧的时刻要解码）、MKV 读写、拼接列表：9.2 MB → 11.4 MB。`tests/test_recorder.py` 用它真录 AV1：录 3 秒、中途断 11 秒（空档保留，事件对得上）、声音对齐（差 0.3 毫秒）、硬杀以后补拼、剪高光（开头是关键帧、180 帧和原片逐帧一样）都过了。还没在游戏里录过。
